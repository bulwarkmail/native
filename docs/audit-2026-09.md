# Native app audit, 2026-09-22

Bugs, performance and webmail gaps in the React Native app, as a TODO list. Every item carries
severity, effort, a `file:line` in this repo (paths relative to `repos/react-native`), the webmail
file to match where there is one (paths relative to the webmail repo root), a repro or measurement,
and whether it was **verified** (reproduced on a device, on the wire or by measurement) or is
**suspected** (code reading only).

Severity: P0 crash / data loss / security, P1 broken feature, P2 degraded, P3 polish.
Effort: S (hours), M (a day or two), L (a week or more).

- **Code:** local `main` at `6c82130` (0.1.62) plus the uncommitted UnifiedPush work in the tree
  (push files only). GitHub `main` is 2 commits ahead (`c2584c2`, `5b8c435`, PR #53: tappable

**Why these ten:**
- **1–2:** security holes that can be exploited today without any user mistake.
- **3–6:** the app silently changes, hides or acts on the wrong mail. When users call the app
  "buggy", this is the class that loses their trust, and all four were reproduced in minutes.
- **7–8:** core flows that fail for every Stalwart user or every share/`mailto:` user.
- **9–10:** the latency users feel on every launch and every tap, the "slow" in "buggy and slow".

Everything else below is narrower (file trees past 500 nodes; tasks, which are off by default),
suspected, or cosmetic.

### Decisions for the maintainer

- **Release signing, before the next version bump:** create the release key, the rotation lineage
  (`apksigner rotate`) and the five repository secrets (`docs/android-release.md`). The release
  workflow now fails without them, and a local release build needs
  `-PallowDebugSignedRelease=true`. `versionCode` is derived from `VERSION` (0.1.62 → 10062).
- **Trusted-sender sync:** the webmail turns "Sync trusted senders to address book" on at login;
  the app now leaves it off until the user turns it on (`d89e331`). Follow the webmail, or keep
  it opt-in?
- **Sender favicons:** still on by default, and the phone fetches them from icons.duckduckgo.com
  itself, having no proxy like the webmail's `/api/favicon`. Default off, a proxy, or keep?
- **Design language:** "Flat fields" and the Tabler icons are not ported (open question below).
- **Short messages:** the quick reply now sits at the bottom of the page so it never jumps
  (`54b169c`), which leaves empty space under a short message.
- **Android app badge:** the icon badge is iOS-only (`25c0883`). On Android, expo-notifications
  clears a badge with `cancelAll()`, which would also dismiss mail notifications and reminders,
  and launchers already badge from the notifications on display.
- **Password hand-off:** taking the password out of the `bulwarkmobile://…#password=` fragment
  needs a one-time code exchange on the webmail (`/api/auth/mobile/handoff` plus a redeem call,
  PKCE-style).
- **Composer font size:** the webmail's font-size picker was left out; it needs a
  selection-rewriting command in the editor page that can only be tested on a device.
- The other open questions at the end (tasks default, office documents, barcode scanner, package
  name, settings sync, feature requests) are unchanged.

## Open questions (product decisions)

- **Tasks** are off by default (`enableCalendarTasks: false`). Should they be on, now that the
  webmail ships them?
- **Design language:** should native follow the webmail's "Flat fields" theme and Tabler icons,
  or keep its own look?
- **Office documents:** WOPI editing (#425) needs the webmail as the WOPI host. Should native open
  office files in Collabora through the webmail, or keep handing them to the OS?
- **Barcode scanner:** the bundled ML Kit scanner costs 5.8 MB and starts with every process,
  including headless pushes. Google's code scanner needs Play services, which conflicts with the
  Google-free UnifiedPush audience.
- **Package name:** `com.anonymous.bulwarkmobile` (Android) vs `org.bulwarkmail.mobile` (iOS).
  This must be decided before any store listing, because changing it later means a new app.
- **Read receipts and the pager:** with neighbour pages pre-rendered, should "Always send" wait
  for the page to be visible for some time, or apply only to the message that was actually
  opened? Decided in `5f3f584`: only the page on screen auto-sends, once per message per session.
- **Settings sync (#1):** needs a server-side store, which neither client has today.
- **Scope of the feature requests:** encryption (#58), widgets (#52), IMAP/SMTP (#51) and native
  sync adapters (#34).
